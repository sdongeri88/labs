# Чекліст огляду коду TaskTracker

Версія 2.0.0 (до стандарту кодування v2.0.0, розділ 7.1). Рецензент проходить усі пункти для кожного pull request у `main`; посилання на правило — у колонці «Правило».

Пунктів, які перевіряє машина, тут немає: відступи, дужки, порядок `using`, регістр імен, `#region`, `#pragma`, `double` і `DateTime.Now` у бібліотеці логіки, довжину рядка, ЦС > 12 і розмір файлу перевіряють аналізатори та `tools/check-style.ps1` у конвеєрі. Якщо конвеєр червоний — огляд не починають.

## Культура огляду

Перше правило: зауваження формулюють до коду, а не до автора — «цей метод змінює стан, хоча названий як запит», а не «ти знову назвав метод неправильно». Друге правило: кожне зауваження виконуване, тобто містить конкретну дію й номер правила — «винесіть 12m у константу `LongEntryHours` (D-06)», а не «незрозуміло». Зауваження без номера правила позначають як «пропозиція» — автор може не виконувати його без пояснень.

## Як записати зауваження

Шаблон: `[R-номер / правило] що не так → що зробити`. Приклади:

- `[R-05 / D-06] 12m у WorkTaskService.AddLog — магічне число → винесіть у константу LongEntryHours`
- `[R-11 / C-08] FromHours кидає ArgumentOutOfRangeException, а <exception> немає → додайте тег з умовою`
- `[R-14] нова гілка NearLimit не покрита тестом → додайте випадок 8 год для оцінки 10 год`
- `пропозиція: TotalHours можна записати через Sum` — без номера правила, виконувати не обов’язково
